Hacking your way through pattern matching on sets

Tristan Brugère

2024-05-14 15:00

A while ago, while writing some code to automate my machine learning pipelines, I ended up writing a function with a definition that looks a bit like this

def check_arguments(provided_arguments: dict[str, Any], required_arguments: list[str]):
    """Checks that the provided set of arguments matches the set of required arguments"""

The pipeline uses this function to check that the hyperparameters it is reading from the config file (or database, etc.) are correct for the model it is loading. But that's beside the point.

This is a pretty common piece of boilerplate one might find anywhere. It simply needs to check that the keys of provided_arguments and the members required arguments contain the same values. Not a very complicated problem, and like all problems in CS, it is trivialised by using the right data structure: the unordered set.

Python being Python, it is right there in the language's basic data structures

def check_arguments(provided_arguments: dict[str, Any], required_arguments: list[str]):
    """Checks that the provided set of arguments matches the set of require arguments"""

    provided_set: set[str] = set(provided_arguments)
    required_set: set[str] = set(required_arguments)

    if provided_set != required_set:
    raise ValueError(f"arguments required are {required_set},"
    "but arguments provided are {provided_set}")

This is already pretty nice and simple, but the error is not very readable. We would like to show the user which arguments were required, but not provided, and which ones were provided, but not required.

Being a functional programmer at heart, I immediately remembered that a few years ago, Python had added pattern matching syntax into the language. So I whipped up a quick solution that ressemled what I would have written in OCaml.

def check_arguments(provided_arguments: dict[str, Any], required_arguments: list[str]):
    """Checks that the provided set of arguments matches the set of require arguments"""

    provided_set: set[str] = set(provided_arguments)
    required_set: set[str] = set(required_arguments)

    match required_set - provided_set, provided_set - required_set:
        case {}, {}: return
        case missing, {}:
            raise ValueError(f"MISSING ARGUMENTS: arguments {missing} were required, but not provided")
        case {}, extra:
            raise ValueError(f"EXTRA ARGUMENTS: arguments {extra} were provided, but not required")
        case missing, extra:
        raise ValueError(f"WRONG ARGUMENTS: arguments {missing} were required, but not provided, "
        "and arguments {extra} were provided, but not required")

The error should be much more readable now, and the code is also very clear and explicit. Surely there is no error with this, right?

The problem

By now, anyone used to working with sets in Python should be banging their head against the keyboard…

You see, Python has a nice syntax for sets: {a1 [, a2 … ]}. It also has a nice syntax for dictionaries: {[k1: v1, ...]}. But they intersect in a very unfortunate way: {} represents an empty dictionary.

Not an empty set. There is no literal syntax for an empty set in Python.

And —very consistently— the pattern matching syntax {} corresponds to the empty mapping pattern.

So never is it going to match the empty set —or any set, for that matter.

At this point I could do the obvious thing: write it into a succession of if-elif-else blocks. But it would be —in my opinion— slightly less readable. Also, where would be the fun in that [1] .

So I set for the way to the syntax for pattern matching on sets, only to find out… there is none. At first I thought "Sets are iterables right? And they have a __len__. So maybe sequence patterns will work?"

Except, as their name indicates, sequence patterns only match sequences (objects that provide __len__ and __getitem__), and sets are not sequences (since they are not ordered).

I had to face it: there is actually no literal pattern to check sets.

Time to hack

That is when I remembered a blog posts I had read a while ago TODO LINK

Python has several ways to hijack instance checking. The easiest and most direct is to create a metaclass that defines a __instancecheck__ method. All classes that are instances of that metaclass will use that method for instance checking.

Exploiting that, one can change the behaviour of class patterns.

Basically we simply have to create a class EmptySet so that isinstance(x, EmptySet) returns True iff x is an empty set.

Anyway, in a dozen lines, I had a working empty set checker:

class CheckerMeta(type):
    check: Callable[[Any], bool]

    def __call__(cls, *args, **kwargs):
        del args, kwargs
        raise ValueError("Class with metaclass CheckerMeta shouldn't be instantiated")

    def __instancecheck__(self, instance):
        return self.check(instance)

class Checker(metaclass=CheckerMeta):
    @classmethod
    def check(cls, instance) -> bool:
        del instance
        return False

class EmptySet(Checker):
    """``isinstance(x, EmptySet)`` checks if x is an empty ``set()`` instance."""
    @classmethod
    def check(cls, instance):
        return isinstance(instance, set) and len(instance) == 0

Now I could write

def check_arguments(provided_arguments: dict[str, Any], required_arguments: list[str]):
    """Checks that the provided set of arguments matches the set of require arguments"""

    provided_set: set[str] = set(provided_arguments)
    required_set: set[str] = set(required_arguments)

    match required_set - provided_set, provided_set - required_set:
        case EmptySet(), EmptySet(): return
        case missing, EmptySet():
            raise ValueError(f"MISSING ARGUMENTS: arguments {missing} were required, but not provided")
        case EmptySet(), extra:
            raise ValueError(f"EXTRA ARGUMENTS: arguments {extra} were provided, but not required")
        case missing, extra:
        raise ValueError(f"WRONG ARGUMENTS: arguments {missing} were required, but not provided,"
        " and arguments {extra} were provided, but not required")

Problem solved! Pretty readable (though sadly not as much as the version that didn't work).

How bad is it, doctor?

Now this is kind of hackish. I'm honestly not sure how I would feel about putting this in code that people other than me may actually use.

On one hand, any code that employs a metaclass raises an alarm in my head. They are a pretty nice abstraction, but I am pretty sure at least 50% of python developers out there have no idea how they work.

On the other hand, this is a pretty short piece of code. It is also pretty clear what it does from the documentation. And it should be pretty easy to understand for someone who actually knows the language features in use here.
